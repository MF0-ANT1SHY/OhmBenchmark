# The 17 non-clear cases: root cause and next action

Companion to `no-clear-difference-forensics.md` (why they failed) and `oracle-coverage.md`
(what was actually collected). This file states, per case, the **single blocking cause** and
the **concrete next action**, and separates what is achievable without a toolchain from what
needs a rebuild.

Status source: `cases/measurement-contract.json` (verdicts regenerated by
`tools/report_oracle_coverage.py`).

### Progress

`satisfied` went from 0 to 4 and `proxy` from 10 to 6 by re-declaring the four oracles

## A. Mechanism absent — not fixable by more measurement (2)

These were tested correctly and the injected bug does not change behaviour on this OS build.
Only a case redesign changes the outcome.

| Case | Evidence | Next action |
| --- | --- | --- |
| `sheafreader_article_list_foreach` | fixture loads **600** articles; only **37** cards build in *both* variants. Control case `browser_history_list_foreach` changes the same `ForEach`→`LazyForEach` and separates cleanly at **200 vs 59** builds over 1000 rows. The unfixed `ForEach` over `List` is already virtualised. | Redesign: either re-declare the oracle to `trace_cpu_ms` (the only field that separates the variants: +11.79%, non-overlapping), or move the counter to the same build stage the browser counter uses and re-verify. Do **not** re-run as-is expecting a difference. |
| `weatherassistant_http_session_leak` | 120 requests through a fresh process; fd counts flat in both variants (71→71, 79→79) against a declared ≥5× growth. | Redesign the fixture: raise request count / force session churn until fd growth is observable, then re-measure; or re-declare the oracle to a quantity that does respond. |

### Re-measurement attempted, and it did not rescue the case

The obvious remedy for `sheafreader_article_list_foreach` — drive real scrolling so that
more rows are built — was tried on the device with the recorded signed builds, staged under
`measurements-staging/` so the original evidence was untouched. It did not work:

| Session | unfixed cards built | fixed cards built |
| --- | --- | --- |
| original 2026-10-01 (3 runs each, no swipes) | 37, 37, 37 | 37, 37, 37 |
| fresh, 3 swipes of `630 2300 -> 630 850` | **31** | **37** |
| control `browser_history_list_foreach` (same change, 1000 rows) | 200, 200, 200 | 59, 59, 59 |

The fresh pair moves in the **wrong direction** (unfixed builds *fewer* cards) and by only
6 cards, against a control that separates by 141. The counter is monotonic in both, so it is
measuring real builds; the variation is scroll-timing dependent, not mechanism dependent.

Conclusion: the scroll drive adds variance, not signal. `List` already defers off-screen row
creation in the unfixed `ForEach` build, so the two variants produce the same
viewport-sized number of cards no matter how the list is scrolled. **The counter is taken at
a stage that cannot separate them**, which is a harness/stage problem, not a
measurement-duration problem. Fixing it means moving the counter (or adding one) to the
stage the control case uses — `ForEach` iterating its data source — and that needs a
rebuild, hence a JRE.

The CPU proxy remains the only collected field that separates the variants
(`trace_cpu_ms`: 4943 ms unfixed vs 4361 ms fixed, +11.79%, non-overlapping).

### Correction: the two "measurement time only" cases are not actually ready

An earlier note here claimed `sepweather` and `wanharmony_html_decode_per_render` needed only
measurement time. **That was wrong.** Verified inventory:

- `device-tests/patches/` contains **18** case directories, and neither of those two is among
  them. The formal measurement harness (the `OhmProbe` bench entry that writes
  `ohm-status.json` and emits `OHMB/*` trace markers) was only ever built for those 18.
- signed HAPs exist for **23** case/variant combinations, and again neither of those two is
  among them.
- What did launch cleanly 9x / 6x for those cases was the **macOS proof loop**
  (`dev/proof-loop` → `tools/device/`), a different harness. Its traces are the 182 release
  assets, and they contain **zero** `OHMB/` markers, so they cannot yield harness-equivalent
  metrics.

Therefore those two cases need a bench entry built and signed like the other group D cases,
and are blocked on the same JRE. The genuinely device-ready work is limited to the 18 cases
that already have both a harness and a signed build — which is exactly the set the earlier
27-case analysis covered.

## Order of work

1. **Free wins, no device, no rebuild:** report the declared counts for group B and re-declare
   the same-quantity oracles in group C. This removes the `elapsed_ms` fallback entirely for
   cases whose declared metric is a count.
2. **Measurement time only:** `sepweather_font_register_per_page`,
   `wanharmony_html_decode_per_render` — existing signed builds, existing counters.
3. **Install a JRE**, then rebuild+sign the group D harnesses that need a new counter, and
   re-run the CloudMusic cases (their host + API fixture must be brought up first).
4. **Case redesign** where the mechanism is absent (group A). This is design work, not
   measurement work.

## Rules this work follows

- A case is only reported as a clear difference when the **declared oracle metric was
  collected** and the unfixed/fixed run ranges **do not overlap**.
- New collection goes to `measurements-staging/` and never overwrites the original evidence
  under the data directory.
- The repository stays reproducible from `hosts_patches/` + `hosts_patches/host-reconstruction.json`
  with no git bundles (`hosts_patches/REPRODUCE.md`).
