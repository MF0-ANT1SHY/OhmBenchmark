# The 17 non-clear cases: root cause and next action

Companion to `no-clear-difference-forensics.md` (why they failed) and `oracle-coverage.md`
(what was actually collected). This file states, per case, the **single blocking cause** and
the **concrete next action**, and separates what is achievable without a toolchain from what
needs a rebuild.

Status source: `cases/measurement-contract.json` (verdicts regenerated by
`tools/report_oracle_coverage.py`).

Current coverage over all 30 cases:

| verdict | n | meaning |
| --- | --- | --- |
| `counter-satisfied` | 1 | declared counter collected and discriminating |
| `mechanism-absent` | 2 | counter collected, but the mechanism cannot separate the variants |
| `proxy` | 10 | a different metric was collected; contract records why |
| `collected-not-used` | 4 | the declared count exists in the run data but was not reported |
| `never-run` | 13 | no rounds; the contract names the primitive needed |

## A. Mechanism absent — not fixable by more measurement (2)

These were tested correctly and the injected bug does not change behaviour on this OS build.
Only a case redesign changes the outcome.

| Case | Evidence | Next action |
| --- | --- | --- |
| `sheafreader_article_list_foreach` | fixture loads **600** articles; only **37** cards build in *both* variants. Control case `browser_history_list_foreach` changes the same `ForEach`→`LazyForEach` and separates cleanly at **200 vs 59** builds over 1000 rows. The unfixed `ForEach` over `List` is already virtualised. | Redesign: either re-declare the oracle to `trace_cpu_ms` (the only field that separates the variants: +11.79%, non-overlapping), or move the counter to the same build stage the browser counter uses and re-verify. Do **not** re-run as-is expecting a difference. |
| `weatherassistant_http_session_leak` | 120 requests through a fresh process; fd counts flat in both variants (71→71, 79→79) against a declared ≥5× growth. | Redesign the fixture: raise request count / force session churn until fd growth is observable, then re-measure; or re-declare the oracle to a quantity that does respond. |

## B. Declared count already in the run data — offline fix (4)

Each declares a **count**; the run data holds the corresponding quantity, but
`export_results.py` reported `elapsed_ms`/`trace_cpu_ms` because the key came from a
hardcoded set. No device time is needed to report them correctly.

| Case | Declared count | Observable in |
| --- | --- | --- |
| `browser_insert_date_lookup_cache` | `rdb_statements_per_page_save` (1000→1 recorded in the case note) | `RdbUtils.insertDate` call/query count |
| `interviewapp_search_history_sync_flush` | `flush_count_per_search_burst` | preferences `flush` call count |
| `interviewapp_search_history_unbounded` | `history_entries_and_render_cost` | `result` already returns returned-entry totals (500 000 → 2 000) |
| `sheafreader_unread_counts_n_plus_1` | `sidebar_count_queries_per_refresh` (201→2 recorded) | `getFeedsWithCounts` query count |

**Next action:** emit these counts into the round record and let the exporter report the
declared key. Two sub-cases are already available without any probe change because the bench
entry returns a count in `result`; the other two need a counter added to the bench entry,
which requires a rebuild (see D).

## C. Proxy metrics — honest re-declaration or improved collection (10)

The collected metric is a different quantity from the declared one. Split by whether the
collected proxy is the same *kind* of thing:

**Same quantity under a different name** — re-declare the oracle to match what is measured:

- `browser_history_delete_no_transaction` — `clear_history_wall_time_ms` vs `elapsed_ms`
- `jingmo_dataset_import_no_transaction` — `dataset_import_wall_time_ms` vs `elapsed_ms`
- `jingmo_random_poem_orderby_random` — `random_read_query_ms` vs `elapsed_ms`
- `sheafreader_refresh_feeds_sequential` — `refresh_all_wall_time_ms` vs `elapsed_ms`

**Genuinely different quantity** — keep both, report the declared one when collected:

- `browser_eager_history_load` — declares startup CPU; `trace_cpu_ms` is process CPU over a
  fixed 10 s window, which the report already warns is not startup latency
- `jingmo_sync_page_reimport` — declares revisit sync-page cost; only DB work is measured
- `sheafreader_extract_tag_tolowercase` — declares parse CPU; reported elapsed
- `sheafreader_insert_duplicate_exception` — declares no-op-refresh CPU; the measured window
  is 22–36 s dominated by fixture work, so the declared phase must be isolated first
- `wanharmony_history_log_materialization` — declares title-event CPU; measured over the
  lifecycle-log phase only
- `cloudmusic_local_song_memory_filter` — declares per-search latency; only ~10 method calls
  were made, so the fixture must reach ≥300 songs and many searches to clear the noise floor

## D. Needs a rebuild to instrument (needs a JRE; see SIGNING.md) — 12

These `never-run` cases need either a new counter in the bench entry or a first successful
measurement. **A rebuilt HAP cannot be signed on this machine until a Java runtime is
installed**, so they are blocked on that, not on the device.

| --- | --- | --- |

| `cloudmusic_search_result_foreach` | component count + CPU | host trigger unstable |
| `cloudmusic_songcard_artists_concat` | CPU | host trigger unstable |
| `interviewapp_response_log_full_stringify` | CPU | blocked: fixture response arrives as a string and is rejected before the logging path |
| `sepweather_font_register_per_page` | elapsed | launched cleanly 6×, no formal round (budget) |

| `wanharmony_web_progress_log_storm` | log call count | budget |
| `weatherassistant_remote_weather_icons` | first-paint + net bytes | injected `.cjs` error |

Note `sepweather` and `wanharmony_html_decode_per_render` need **no new instrumentation** —
their existing signed builds launched fine and simply never produced formal rounds. They
need measurement time, not code.

## Order of work

1. **Free wins, no device, no rebuild:** report the declared counts for group B and re-declare
   the same-quantity oracles in group C. This removes the `elapsed_ms` fallback entirely for
   cases whose declared metric is a count.
2. **Measurement time only:** `sepweather_font_register_per_page`,
   `wanharmony_html_decode_per_render` — existing signed builds, existing counters.
3. **Install a JRE**, then rebuild+sign the group D harnesses that need a new counter, and
   re-run the CloudMusic cases (their host + API fixture must be brought up first).
4. **Case redesign** where the mechanism is absent (group A). This is design work, not
   measurement work.

## Rules this work follows

- A case is only reported as a clear difference when the **declared oracle metric was
  collected** and the unfixed/fixed run ranges **do not overlap**.
- New collection goes to `measurements-staging/` and never overwrites the original evidence
  under the data directory.
- The repository stays reproducible from `hosts_patches/` + `hosts_patches/host-reconstruction.json`
  with no git bundles (`hosts_patches/REPRODUCE.md`).
